# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`ithink-mq-web` is a Spring Boot 4.1.1 (Java 21) web app for browsing IBM MQ queues and searching the messages it has pulled off them. Server-rendered UI via Thymeleaf + the Thymeleaf Layout Dialect, styled with Bootstrap 5 loaded from a CDN (no frontend build step, no static asset pipeline). The MQ browse flow, local persistence, and full-text search are implemented; only IBM MQ publish/put functionality is out of scope so far.

## Commands

Use the Maven wrapper (`mvnw`), not a system-installed Maven.

- Run the app: `./mvnw spring-boot:run` (starts on the default port, 8080)
- Build: `./mvnw clean package`
- Run all tests: `./mvnw test`
- Run a single test class: `./mvnw test -Dtest=iThinkMqWebApplicationTests`
- Run a single test method: `./mvnw test -Dtest=iThinkMqWebApplicationTests#contextLoads`

The app creates a `./data` directory on startup (for the SQLite file) — this is gitignored.

## Architecture

- **Everything lives under `hu.ithink.mq`**, split by layer: `controllers`, `services`, `repositories`, `entities`, `models`, `exceptions`. There is no separate top-level package root anymore — new classes should nest under `hu.ithink.mq.<layer>`, matching the existing classes in that layer.
- **Controllers are package-private** (e.g. `IndexController`, `MessageController`, `ConnectionProfileController`, `TestDataController` have no `public` modifier) — keep this convention for new controllers.
- **Form-backing and read-only view models are plain Java `record`s** (`MqConnectionModel`, `MessagePage`, `MessageRow`) — Spring Framework's data binder supports constructor binding to records for `@ModelAttribute`/`th:field`, so no Lombok is needed there; give a record a no-arg auxiliary constructor (delegating to the canonical one) if a controller needs to hand Thymeleaf an empty instance. JPA entities (`Message`, `ConnectionProfile`) use Lombok's `@Data` instead, since they need mutability; both are also used directly as form-backing/view objects in their templates (`message-view.html`, `connection-profile/add.html` + `edit.html`) rather than introducing separate DTOs.
- **Thymeleaf layout pattern**: `templates/layout/base.html` is the master layout (HTML shell, CDN Bootstrap CSS/JS, the global `confirm-submit.js` script, a `layout:fragment="content"` slot, `layout/header`/`layout/footer` fragment includes, and an optional `layout:fragment="scripts"` slot for page-specific `<script src="...">` tags). Individual pages use `layout:decorate="~{layout/base}"` and fill in `layout:fragment="content"`. Templates are grouped by feature area: `templates/layout/` (base, header, footer), `templates/message/` (`index.html`, `messages-table.html` — the `th:fragment="table"` reused both by the index page and returned directly from the live-search AJAX endpoint, `message-view.html`), `templates/connection-profile/` (`list.html`, `add.html`, `edit.html`, and `form.html` — a `th:fragment="fields"` with the shared host/port/queue-manager/etc. inputs, included by both `add.html` and `edit.html` so the field set only exists once). Reuse these fragments rather than duplicating markup in new pages.
- **No inline `<script>` blocks** — JS lives in `src/main/resources/static/js/*.js`, one file per template that needs page-specific behavior (`header.js`, `message-index.js`), referenced via `<script src="/js/...">`. `confirm-submit.js` is the one exception loaded globally from `base.html`: any `<form>` with a `data-confirm="..."` attribute gets an automatic confirm-dialog-before-submit, so templates don't need their own inline `onsubmit` handlers for delete confirmations — just add the attribute.
- **Persistence**: SQLite (via `org.xerial:sqlite-jdbc` + `hibernate-community-dialects`' `SQLiteDialect`) at `./data/ithink-mq.db`, with schema managed by Liquibase (`db/changelog/db.changelog-master.xml` includes each `db/changelog/changes/NNN_*.xml` file in order; `ddl-auto` is `none`). Add new schema changes as new changesets/files rather than editing already-applied ones. The `message` table has a companion `message_fts` FTS5 virtual table (trigram tokenizer, external-content, kept in sync via `AFTER INSERT/UPDATE/DELETE` triggers) used for fast substring search over id/content/properties. The `connection_profile` table (`001_connection_profile.xml`) has no such index — it's small, browsed in full. Its `id` column is `INTEGER PRIMARY KEY AUTOINCREMENT` (`GenerationType.IDENTITY` on the entity) rather than `GenerationType.SEQUENCE`, since SQLite has no native sequence support.
- **Data access is split two ways for messages, plain JPA for connection profiles**: `MessageRepository` (`JpaRepository<Message, String>`) backs simple CRUD, used by `MessageService` (find by id, save all, delete by id, purge all). `MessageQueryService` bypasses JPA and uses `NamedParameterJdbcTemplate` directly with hand-written SQL, because paginated/previewed full-text search against the FTS5 virtual table doesn't map well onto Spring Data derived queries; it also falls back from an FTS `MATCH` query to a `LIKE` query for search terms under 3 characters, since SQLite's trigram tokenizer can't match those. `ConnectionProfileRepository`/`ConnectionProfileService` are a thin, ordinary `JpaRepository` CRUD wrapper (no custom queries needed — the profile list is small and always read in full, sorted by name).
- **MQ browsing**: `MqQueueBrowseService` connects to IBM MQ (via `com.ibm.mq.allclient`) using the client transport, non-destructively browses every message currently on a queue (`MQOO_BROWSE`, so messages stay on MQ). On success it wholesale-replaces the local `message` table (`MessageService.purgeAll()` then `saveAll(...)`) so every load reflects exactly what's on the queue rather than accumulating stale rows; the purge only happens *after* a successful browse, so a failed connection/browse never wipes existing data. MQ message properties (format, priority, persistence, correlation/group IDs, put date/time, etc.) are serialized to JSON in the `properties` column. Connection/browse failures are wrapped in `MqBrowseException` and surfaced as a flash-style alert on the index page.
- **Connection profiles**: `ConnectionProfile` (entity, `connection_profile` table) is a saved/named preset of the fields in `MqConnectionModel` — `name`, `host`, `port` (`int`), `username`, `password`, `queueManager`, `channel`, `queue`. `ConnectionProfileController` (`/connection-profile`) provides full CRUD: `GET` list, `GET`/`POST /add`, `GET`/`POST /{id}/edit`, `POST /{id}/delete` (404 via `ResponseStatusException` if an edit target doesn't exist). The index page (`GET /`) is handed the full profile list as `connectionProfiles` and renders it as a `<select id="connectionProfileSelect">` with one `data-*` attribute per connection field on each `<option>`; `static/js/message-index.js` listens for `change` on that select and copies the chosen option's `data-*` values into the matching `MqConnectionModel` form fields (matched by input `id`, which Thymeleaf's `th:field` already derives from the property name) — nothing server-side is involved in the prefill, it's pure client-side. Note the saved password ends up in the rendered `data-password` attribute (and, after prefill, in the visible password input's value) — no worse than the existing `MqConnectionModel` form already doing the same on re-render, but worth knowing if this app is ever exposed beyond localhost.
- **Controller flow**: `GET /` renders `message/index` with an empty `MqConnectionModel`, the first page of stored messages, and the connection profile list; `POST /load` re-binds the submitted `MqConnectionModel`, triggers `MqQueueBrowseService.browseAndStore`, and re-renders the same view with a success/error message. `GET /messages/search` returns just the `message/messages-table :: table` fragment for the debounced/button-triggered live-search input in the header. `GET /messages/{id}` shows a single message's full content/properties; `POST /messages/{id}/delete` and `POST /messages/purge` delete one or all stored messages. Both the messages table and the connection-profile list group their row actions with Bootstrap's `.btn-group`.
- **Test data**: `TestDataController` (`POST /test-data/load`) is a plain `@ResponseBody` endpoint (returns a status string, not a redirect) wired to the "Load test data" button in the header via `fetch` + `alert(...)` (currently hidden behind Bootstrap's `d-none` on the button — re-enable by removing that class), so it works from any page. `MqTestDataService` connects with the hardcoded dev queue connection (see below, not a saved `ConnectionProfile` or the form) and MQ-PUTs a batch of generated sample JSON payloads onto the queue — it doesn't touch the local `message` table; a user still browses them in via the normal `POST /load` flow afterwards. Put failures are wrapped in `MqPutException` (mirrors `MqBrowseException`, but kept separate since put/browse are different failure domains).
- **User-facing strings (flash messages, template labels, confirm dialogs) are in English** — match this when adding new UI text or error messages.
